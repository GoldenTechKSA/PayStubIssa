# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

PayStubIssa (`pay-stub`) is a Create React App (react-scripts) + TypeScript single-page app for generating, previewing, and printing/PDF-exporting US pay stubs, gated behind a PayPal payment. It is deployed to a Hostinger VPS (Apache2, docroot `/var/www/paystubissa.com`) by a GitHub Actions workflow that builds and rsyncs `build/` on push to `master` — see [docs/deploy/DEPLOYMENT.md](docs/deploy/DEPLOYMENT.md). `homepage` in package.json is `"/"`: the site is served from the domain root, so asset paths are absolute (`/static/...`). Keep it that way; the old `"."` was a leftover from subfolder FTP hosting.

## Commands

```bash
npm install            # install deps (run after pulling new changes)
npm start              # dev server on http://localhost:3000
npm run build          # production build to ./build
npm test               # CRA/Jest watch mode (run a single file: npm test -- buildPaystubModel)
npm run api            # Node API dev server on http://localhost:4000 (payments + telemetry; CRA proxies /api to it)
npm run api:test       # server vitest suite
```

Quick template/PDF check without the wizard or a payment: `npm start`, then open `http://localhost:3000/create?dev=unlock`. It lands on the Review step with print and Download PDF unlocked (`isDevUnlock` in [dev-flags.ts](src/utils/dev-flags.ts), dead code in production builds). The dev seed is a complete bi-weekly example, but a saved draft in localStorage still wins over it. The API on port 4000 is not needed for this; the price falls back to the local constant and telemetry posts fail quietly.

A committed `.npmrc` sets `legacy-peer-deps=true` so a plain `npm install` works: react-scripts 5 declares a stale peer dependency on TypeScript 4, but the project runs on TypeScript 5 (which CRA 5 builds and tests fine). Don't remove `.npmrc` without addressing that conflict.

There is **no separate lint script**; ESLint runs through `react-scripts` (`eslintConfig`: `react-app`, `react-app/jest`). Debugging: `npm start`, then use the "Launch Chrome against localhost" config in VS Code Run & Debug (`.vscode/launch.json`).

## Data flow

State lives in a plain Redux store (`redux/store.tsx`, classic `createStore` + `combineReducers` — not Redux Toolkit slices despite RTK being a dependency). Five slices: `appSettings`, `companyInfo`, `employeeInfo`, `incomeDetails`, `generalInfo` (shapes in [pay-stub-details.ts](src/assets/data/pay-stub-details.ts)).

- The store is **seeded with different initial state per environment**: `production-initial-state` in production, `initial-state` (pre-filled dev data) otherwise — selected in [store.tsx](src/redux/store.tsx) via `NODE_ENV`.
- Each reducer responds to a single `SAVE_*` / `UPDATE_APP_SETTINGS` action ([action-types.tsx](src/constants/action-types.tsx), [actions.tsx](src/redux/actions.tsx)) and merges its payload (`{...state, ...payload}`). Actions are untyped (`data` is `any`).
- The user flow is a **6-step MUI stepper wizard** at `/create` ([PaystubWizard.tsx](src/components/wizard/PaystubWizard.tsx)): Company → Employee → Pay period → Earnings → Template → Review. Each step ([src/components/wizard/steps/](src/components/wizard/steps/)) reads its slice with `useSelector`, validates locally (inline on blur), and dispatches its `SAVE_*` action on Next. The wizard autosaves a draft to `localStorage` (key `paystubissa.draft.v1`) and rehydrates it on return; it also defaults `appSettings.configPath` to `template-simple` so the preview renders.
- Routing is in [app.tsx](src/components/app.tsx): `/` (hero), `/create` (wizard), `/offers` (tiered price cards), `/aboutUsPage`, `/FAQPage`, `/contactUsPage`, `/privacy`, `/accessibility`, `/terms`, and a `*` not-found. The header/footer use a `no-print` class; the Review step's print path isolates the pay stub (see PDF/print below).
- Use `useSelector`/`useDispatch` for state access. (The old tabbed `/appBody` flow and the Bootstrap screens that read `store.getState()` at render time have been removed.)

## Paystub rendering — XML config system

The rendered pay stub is **data-driven from XML**, not hard-coded React. This is the single rendering path:

1. The wizard's **Template step** ([TemplateStep.tsx](src/components/wizard/steps/TemplateStep.tsx)) reads [public/configs/template-configs.json](public/configs/template-configs.json) — an array where each entry has a `configFile` path (e.g. `/configs/template-simple/paystub-config.xml`) plus image/title/description. Selecting a template dispatches `{ configPath, templateId }` into `appSettings`. (Its `AVAILABLE_CONFIGS` set gates which entries are selectable/previewable; today it lists all 8.)
2. The Template step and the **Review step** ([ReviewStep.tsx](src/components/wizard/steps/ReviewStep.tsx)) render `<TemplateManager configPath={configPath} store={fullState} />` for the live preview.
3. [templatemanager.tsx](src/templates/components/templatemanager.tsx) builds the data model via `buildPaystubModel(store)` (see Tax & data model below), fetches the XML via `loadPaystubConfig`, validates it, and renders `<PaystubRenderer config data />`.
4. [xmlParser.ts](src/templates/components/paystub/xmlParser.ts) parses XML → `PaystubConfig` (`sections → columns → tables → cells`). It still resolves `<include href="...">` elements (depth-limited, cycle-guarded), but no shipped template uses them any more — see the one-file convention below.
5. [PaystubRenderer.tsx](src/templates/components/PaystubRenderer.tsx) → `Section` → `Column` → `Table` → `TableCell` ([src/templates/components/paystub/](src/templates/components/paystub/)) render the parsed config; per-element inline `<style>` from the XML becomes React inline styles.

**Cell binding & formatting** ([TableCell.tsx](src/templates/components/paystub/TableCell.tsx)). A cell has a `type` and an optional `format`:
- `type="static"` — literal label text.
- `type="substitute"` — `{path.to.field}` placeholders resolved against the data model (e.g. `{incomeDetails.hourlyRate}`, `{grossPay}`, `{federalTaxYTD}`).
- `type="calculated"` — `{field}` placeholders resolved, then the arithmetic expression is safely evaluated.
- `format="currency | number | date | text"` — presentation applied by the renderer to the resolved value. The data model holds **raw numbers**; templates decide display. `currency` → `$1,234.56`, `number` → `1,234.56`, `date` → `MM/DD/YYYY`. `calculated` cells default to `currency` when `format` is omitted.

XML config files live in [public/configs/](public/configs/). **One template = one file**: each `template-<name>/` folder holds a single, pretty-printed `paystub-config.xml` with every section inline (one element per line, a `<!-- Section <id>: ... -->` comment above each top-level section). Do not split a template into `<include>` partials. `template-configs.json` lists all 8 templates; `template-simple` is the reference layout. Each entry's `imageFile` is a real thumbnail of the template (`public/images/templates/thumb-<name>.png`, the top 720×560 px of the rendered stub at half scale) made by `node scripts/make-template-thumbs.js [<template-name>]`, which also rewrites `imageFile`; re-run it after changing a template's layout or adding one. The 26 placeholder templates retired on 2026-10-18 were one skeleton in cosmetic skins; their gallery titles/descriptions are kept in [docs/templates/TEMPLATE-CATALOG-BACKLOG.md](docs/templates/TEMPLATE-CATALOG-BACKLOG.md) as the audience list for real templates to come. After editing any config run `node scripts/format-template-configs.js` to re-normalise it (`--check` fails if a file is not in canonical form), and `npm test -- template-configs` to confirm every template still loads and validates. When changing a template, keep cell `{paths}` in sync with the `PaystubModel` contract.

## Tax & data model

The renderer consumes a single computed model assembled by [buildPaystubModel.ts](src/templates/utils/buildPaystubModel.ts) — `buildPaystubModel(store) → PaystubModel`. This is the only data the XML binds to, so it is the contract: extend `PaystubModel` ([pay-stub-details.ts](src/assets/data/pay-stub-details.ts)) and `buildPaystubModel` together, and templates reference those field names. `PaystubModel` spreads the raw store (so `{incomeDetails.*}` etc. still resolve) and adds period-current numbers plus a `*YTD` sibling for each: earnings (`regularPay`, `overtimePay`, `otherEarnings`, `grossPay`), taxes (`federalTax`, `stateTax`, `socialSecurity`, `medicare`, `totalTaxes`), deductions (`medical`, `dental`, `vision`, `retirement401k`, `otherDeductions`, `totalDeductions`), and `netPay`. All values are raw numbers — never pre-formatted.

`buildPaystubModel` reuses the calculation utilities rather than duplicating logic:
- [tax-calculator.ts](src/utils/tax-calculator.ts) (`taxCalculator` singleton) — federal income tax withholding by the IRS Publication 15-T percentage method for a standard W-4 (Step 2 unchecked, nothing in Steps 3–4), Social Security (wage-base capped), Medicare (+ additional Medicare over a filing-status threshold), and state income tax (flat/bracket) from [state-tax-data.ts](src/assets/data/state-tax-data.ts). The federal tables and the Social Security wage base are **per calendar year** in [federal-tax-data.ts](src/assets/data/federal-tax-data.ts) (2024–2026 on file, each filing status its own schedule), picked by the year of the stub's **pay date**; a year outside the range uses the nearest one. **Add the new year every December** when the IRS issues the next Publication 15-T — [federal-tax.test.ts](src/__test__/federal-tax.test.ts) checks each schedule against the IRS's tentative-amount column, so extend it with the new year's figures. Medicare rates are read from the `'AL'` entry since they are identical across states.
- `calculateOvertime` ([overtime-calculator.ts](src/utils/overtime-calculator.ts)) and the period helpers `periodsPerYear` / `periodsToDateThisYear` ([date-calculator.ts](src/utils/date-calculator.ts)).

Key model behaviors:
- **Gross basis**: full earnings — regular + overtime + bonus, or `annualSalary / periodsPerYear` when `wageType === 'Salary'`.
- **Annualize for tax, then de-annualize**: the tax engine expects annual income (annual standard deduction + annual brackets), so the period gross is multiplied by `periodsPerYear`, taxed, then divided back to the period. Without this, federal/state withholding comes out ~0.
- **Percent-of-gross deductions**: `incomeDetails.deduction401k` and `incomeDetails.unionDues` are stored as a **fraction of gross** (the Earnings step takes a percentage; 5% is `0.05`), and the model turns them into dollars (`retirement401k`, `unionDues`). The 401(k) is traditional/pre-tax: it lowers the wages federal and state income tax are withheld on, but not Social Security, Medicare or paid leave. Union dues are after-tax, count in `totalDeductions`, and are folded into `otherDeductions` (the catch-all "Other" line); a template with its own union-dues row binds `otherDeductionsExUnion` for its Other row instead (`template-ledger-classic` does).
- **Pay date**: defaults to period end + 7 days, is user-editable, and may never be before the period end. The gap the user picks on stub #1 (`payDateGapDays`) is applied to every stub in a run.
- **Total Taxes = the printed lines**: `totalTaxes` is federal + state + Social Security + Medicare + `paidLeave` (a state paid-leave premium, 0 in most states), each rounded to the cent. A template that prints the tax breakdown must print the paid-leave line too (`{paidLeaveLabel}`, `{paidLeave}`, `{paidLeaveYTD}`), normally as `<rowcells renderIf="paidLeave">` — `renderIf` works on a single table row as well as on section/column/table. [template-configs.test.ts](src/__test__/template-configs.test.ts) fails otherwise.
- **Filing status**: `employeeMarriedStatus` is passed through as the IRS `FilingStatus` (`single | marriedFilingJointly | marriedFilingSeparately | headOfHousehold`, matching [filing-status.json](src/assets/data/filing-status.json)), with legacy "Married" normalized. `FilingStatus` is **not** `'single' | 'married'` — using `'married'` produces `NaN`.
- **YTD** is an estimate, not a payroll-history accumulation, with two kinds of line. *Recurring* lines (regular pay, the withholding on regular pay alone, every deduction) are `per-period × periodsElapsedAt(pay date)`. *One-time* lines (overtime, bonus, and the extra tax they drew) are counted once: on the stub that pays them and, carried forward, on every later stub in the run. Only period #1 of a multi-stub run pays overtime/bonus; later stubs get 0 of each. The identities `grossYTD = regularYTD + overtimeYTD + bonusYTD` and `netYTD = grossYTD − taxesYTD − deductionsYTD` hold on every stub.

## Review, payment, PDF/print, telemetry

The wizard's **Review step** ([ReviewStep.tsx](src/components/wizard/steps/ReviewStep.tsx)) is the finalize screen: a read-only summary (with Edit buttons that jump back to a step), the computed pay totals from `buildPaystubModel`, a live preview, the payment gate, and print/PDF.

- **Payment gating**: print/PDF are gated by `appSettings.canPrint`, flipped to `true` on PayPal success. The preview shows a "PREVIEW" watermark until paid. The reusable `<PayPal>` ([paypal-payment.tsx](src/components/common/paypal-payment.tsx)) renders PayPal buttons via the `window.paypal` SDK loaded in [public/index.html](public/index.html). The server (`server/`) quotes the cart, creates and captures the PayPal order, verifies the captured amount, and issues a signed unlock token that the client keeps in `sessionStorage` and re-verifies on reload; the raw capture is stored on the order row. **Coupons**: the Review step has a "Coupon code" field; the applied code rides on the quote and the order, and the server is the only judge of it. Codes are percent-off only and come from the server's `COUPONS` env var (`CODE:PERCENT,...`, 1–99, parsed by `parseCoupons` in [server/src/config.ts](server/src/config.ts) — 100% is refused because a $0 order has no PayPal path). Telemetry reports only that a coupon was applied or rejected (`[1309]`/`[1310]`), never the code text.
- **Prices are set on the server only, as a tier table.** `PRICE_TIERS` (`MINQTY:CENTS,...`, default `1:899,2:799,5:699,9:599` in [server/src/config.ts](server/src/config.ts), overridable in the VPS `.env`) gives the price of ONE stub by how many are in the order; **every stub in the order is charged at the tier the quantity falls in** (`unitCentsFor` in [server/src/services/pricing.ts](server/src/services/pricing.ts)), and a coupon's percentage comes off that subtotal. `parsePriceTiers` stops the API at boot unless there are at least two tiers, the first starts at 1, quantities rise and prices **fall** from tier to tier — the Offers page says "Best value" and "Save $X" on the strength of that. The retired `PRICE_PER_STUB_CENTS` is ignored with a boot warning. The client holds no price; do not add one back ([price-context.test.tsx](src/__test__/price-context.test.tsx) fails on any dollar amount in `src/` or a literal price in `public/index.html`, so comments must not spell one either). Every mention reads [price-context.tsx](src/contexts/price-context.tsx) (`usePrice()` → `tiers`, `unitCents`/`label` for a single stub, `fromCents`/`fromLabel` for the lowest tier, `priceFor(qty)`; `<Price>` / `<Price from>`), which is **stamped-plus-live**: [scripts/stamp-price.js](scripts/stamp-price.js) runs as `prebuild`/`prestart`, asks `PRICE_SOURCE_URL/api/payments/config` (the deploy workflows pass the site's own URL) and writes `REACT_APP_PRICE_TIERS` (JSON), `REACT_APP_STUB_PRICE` and `REACT_APP_STUB_PRICE_FROM` to a gitignored `.env.*.local`, so the first paint and the `<meta>` descriptions in `index.html` ("From $X per stub") carry prices; a server that is unreachable **or answers without tiers** (the client is built before the API is replaced) falls back to the `PRICE_TIERS` default in `config.ts`. `PriceProvider` then fetches `GET /api/payments/config` on every visit and swaps in the live table (remembered in localStorage while the build stamp is unchanged). `/config` sits ahead of the payments rate limiter for this reason. With no stamp and no answer the pages print number-free wording, never a guess. Changing a price = change `PRICE_TIERS` and restart the API; pages follow on the next visit, the `<meta>` text on the next deploy. The Terms of Use name no amount (the price depends on the order size and is "shown to you at checkout before you pay").
- **Offers page** (`/offers`, [offers-page.tsx](src/components/common/offers-page.tsx)): one card per tier of the server table. The words live in [offer-cards.ts](src/components/common/offer-cards.ts); the four named cards (Single Stub, Starter Pack, Quarter Pack, Full Run) describe the ranges 1 / 2–4 / 5–8 / 9–12 and are used only while the server's ranges are exactly those (or prices are unknown, when they show without a number); any other table gets generic "N–M Pay Stubs" cards. A card's "Make yours now!" opens `/create?stubs=N`; the wizard applies N to `generalInfo.payStubCount` over a saved draft's count only, then drops the parameter. The home page keeps its single-price card and badge and adds the orange "Bundle and Save" button (`BundleButton` in [price-copy.tsx](src/components/common/price-copy.tsx), palette colour `bundle` — the only orange on the site, slate text for contrast; the Offers page's green is `success.dark`, because `success.main` with white fails WCAG AA at text size) beside the main button and inside the pricing card. Shared price sentences (`PriceSummary`, `StubExample`, `OffersLink`) are in the same file.
- **PDF / print**: `<PDFDownloadButton>` ([pdf-button-comp.tsx](src/components/pdf/pdf-button-comp.tsx)) snapshots the `#pdf-content` node with `html2canvas` + `jspdf`. Print uses `window.print()` after adding a `print-paystub` body class; [print.css](src/components/wizard/print.css) then isolates `#pdf-content` so only the pay stub prints.
- **One stub, one sheet — a hard rule for every template.** A template MUST fit on a single US Letter (8.5×11 in) page. `print.css` sets `@page { margin: 0.5in; size: letter }` and prints `#pdf-content` at full size, so each `.paystub-page` gets exactly **7.5 × 10 in = 720 × 960 CSS px** at 96 dpi. Anything taller silently spills onto a second sheet; the PDF button hides the problem instead of showing it, because it scales each page down to fit and just shrinks the type. Design to the 720 px width, not to the width of a reference screenshot — a mockup captured at ~1000 px has to come down by ~0.7× in both type and spacing or it will overflow. Budget the vertical stack (section margins + paddings + row heights) and leave ~10% headroom for text that wraps at the narrower print width. `template-simple` uses ~710 px and `template-modern` ~835 px (its summary box shares the Deductions row — the Deductions column carries the `renderIf`, so the summary survives a stub with no deductions). [FitPage.tsx](src/components/wizard/FitPage.tsx) previews at that same 720 px so the Review step's “exactly what will print” is true. The gray “desk” around the sheet is a flex row with a `maxHeight`; it must keep `alignItems: "flex-start"`, because a single-line flex container clamps its line to its max-height and stretches items to it, which pinned the sheet at its min-height while the stub ran on past the sheet's bottom edge. **The printed stub is only pinned to the page while nothing between `#pdf-content` and the page is positioned** — it is `position: absolute; top: 0`, so a `position: relative` ancestor silently makes it start wherever that ancestor sits on the review page and run off the bottom. `print.css` resets the sheet and the scaler wrappers (`.paystub-sheet`, `.paystub-fit-outer`, `.paystub-fit-box`) for exactly this reason; anything new wrapping the preview needs the same treatment. The PDF path needs it too: html2canvas neutralises `transform` only inside the subtree it captures, so with FitPage's scaler left on an ancestor it measures the clone at the shrunken preview size but paints glyphs at full CSS size — words overlap and the right edge is clipped. `PDFDownloadButton` therefore runs `unscaleFitPage` (exported from `FitPage.tsx`) in html2canvas's `onclone`; keep it in step with the print.css reset. To check a change for real run `node scripts/snapshot-templates.js <template-name>`: it renders the template with realistic sample data into `.snapshots/<name>.png` (720 px wide, red line at the 960 px page bottom) and `.snapshots/<name>.pdf` through the real print path, and reports the PDF page count — one stub must be one page. As of 2026-10-18, all 8 templates print on one page (`template-ledger-classic`, the Temporary Assignment stub, uses ~735 px). The script also prints `review-shell`: the first template inside a model of the Review step's ancestor chain (app shell, stepper, summary column, sheet, FitPage wrappers) with the body classes the print button adds, and it must be one page too. It guards a different failure: `print.css` hides the rest of the review page with `visibility`, which keeps it **in layout**, so the document once paginated to the review page's on-screen height and the stub came out followed by blank sheets carrying only the browser's header/footer. `print.css` collapses `#App` to zero height in print for that reason; the stub survives because it is positioned against the page, not against `#App`. **A multi-stub run is paged on screen, printed in full.** The Review step renders every stub of the run inside `#pdf-content` but shows only the one its pager ([StubPager.tsx](src/components/wizard/StubPager.tsx): arrows, "Pay stub k of N" with dates, numbered dots, arrow keys, swipe) points at; `TemplateManager`'s `activeStub` prop puts `paystub-page-inactive` on the others, which `print.css` hides on screen and reveals again in print, and `PDFDownloadButton` strips in html2canvas's `onclone` (`revealAllPages`). The snapshot script also prints `review-shell-run` for exactly this: a run of three with the two before the active one hidden, and it must come out as **three** sheets.
- **Telemetry**: every event carries a **site code** `[NNNN]` that identifies the one place in the code that emitted it. Codes are declared once, in a registry per side: client `1000–1999` in [src/telemetry/codes.ts](src/telemetry/codes.ts) (`T.WIZARD_STEP_COMPLETED` etc.), server `2000–2999` in [server/src/telemetry/codes.ts](server/src/telemetry/codes.ts). **One emit site per code** — add a new registry entry before emitting from a new place; the registry tests reject duplicates and non-allow-listed prop keys. The browser emits with `telemetry.emit(T.X, props)` ([telemetry-service.ts](src/services/telemetry-service.ts)): batches of 10 / every 10 s to `POST /api/telemetry`, a `sendBeacon` on unload, a visitor id in localStorage and a per-visit session id in sessionStorage (30-min idle rollover); `emit` is a no-op under `NODE_ENV=test`. `TelemetryProvider` ([telemetry-context.tsx](src/contexts/telemetry-context.tsx)) starts it once with the module-level `TELEMETRY_CONFIG` in `app.tsx` (console echo in development); `RouteTelemetry` reports navigation. The server route ([server/src/routes/telemetry.ts](server/src/routes/telemetry.ts)) validates with zod, scrubs PII ([scrub.ts](server/src/telemetry/scrub.ts) — a `[2003]` log line means the client leaked something), and inserts into `telemetry_events`; the payments router logs `21xx` milestones under the browser's session via the `X-Telemetry-Session` / `X-Telemetry-Visitor` headers that `payments-api.ts` sends. The `telemetry_sessions` view gives one funnel row per visit. Read it on the VPS with `node scripts/query.js sessions|timeline <id>|funnel|errors|paid` (see [server/README.md](server/README.md)). Env: `TELEMETRY_ENABLED` (kill switch), `TELEMETRY_RETENTION_DAYS` (default 90). **Never emit form values** — ids, counts, amounts, codes and messages only. Design: [docs/superpowers/specs/2026-10-17-telemetry-pipeline-design.md](docs/superpowers/specs/2026-10-17-telemetry-pipeline-design.md).

## Legal copy and business identity

Every legal statement on the site has to stay true to what the code does; false privacy or marketing copy is itself legal exposure. Conventions, settled with the owner and a lawyer on 2026-11-01:

- [business-info.ts](src/constants/business-info.ts) is the single source for the operator's identity (GOLDENTECH KSA L.L.C., a Washington LLC; Washington law and courts; the registered agent's mailing address; support phone and emails) and for the three load-bearing sentences (`CORE_DISCLAIMER`, `FRAUD_WARNING`, `ATTESTATION_TEXT`). Never restate them elsewhere.
- The legal pages are [terms-of-use.tsx](src/components/common/terms-of-use.tsx), [privacy-policy.tsx](src/components/common/privacy-policy.tsx) and [accessibility-policy.tsx](src/components/common/accessibility-policy.tsx). When either policy changes materially, bump `POLICIES_LAST_UPDATED` and `POLICIES_VERSION` together; the version is sent with every order as `termsVersion` and stored next to `attestedAt`, so each purchase shows which Terms were agreed to.
- **Checkout is clickwrap.** The Review step's single box reads "I have read and agree to the Terms of Use and Privacy Policy, and ${ATTESTATION_TEXT}" with both documents linked, and payment is not offered until it is ticked ([review-attestation.test.tsx](src/__test__/review-attestation.test.tsx) guards this). Keep it that way: terms that only sit behind a footer link are rarely enforced.
- **The Privacy Policy must describe what the server actually stores.** Today that is the `orders` row (quote, coupon code, PayPal capture JSON with the payer's name and email, IP, user agent, attestation time, Terms version) kept for `ORDER_RETENTION_DAYS` (default 1095 = the three years the policy promises; `OrderService.prune()` runs at boot and daily) and telemetry events for 90 days. Pay stub data never reaches the server. If a new field starts flowing to the server, update the policy in the same change.
- Phone numbers and postal addresses are plain text everywhere, never `tel:` links and never coloured; only email addresses and page URLs are links. On the legal pages the contact block (address, phone, emails) is the last block on the page, after the Acknowledgment.
- Marketing claims must be literally true: `TEMPLATE_COUNT` must equal the gallery ([template-configs.test.ts](src/__test__/template-configs.test.ts) fails otherwise); do not claim credentials (accountants, payroll experts) or acceptance by any third party; never use "proof of income" or similar phrasing.
- Every stub template prints "Prepared from information supplied by the employer. For informational purposes only; not a negotiable instrument." in its footer (the contractor statement says "payer"). A new template needs the same line and must still pass the one-page check.

## UI / design system (MUI)

The UI is **Material UI (MUI 7)** end-to-end — React-Bootstrap has been removed. A single theme ([src/theme/theme.ts](src/theme/theme.ts)) defines the design tokens (Trust Blue `#2563EB` primary, Profit Green `#059669` success, slate text, IBM Plex Sans/Mono) and is applied via `ThemeProvider` + `CssBaseline` in [index.tsx](src/index.tsx). Style with `sx`/theme values, not raw hex or CSS classes. ## Conventions

- TypeScript `strict` is on, but `noImplicitAny: false` — Redux actions/reducers and some event handlers are intentionally untyped `any`. `baseUrl: "src"` enables absolute imports like `import { ... } from 'assets/data/pay-stub-details'`.
- File naming is **kebab-case** for most code (`tax-calculator.ts`, `app-header.tsx`), but the `src/templates/` tree and some wizard files use other casings (`templatemanager.tsx`, `buildPaystubModel.ts`, `PaystubWizard.tsx`).
- `process.env.NODE_ENV` is used directly to branch dev vs prod behavior (initial state). There is no committed `.env` (`.env.development` / `.env.production` are gitignored).
- Reference data (states, filing statuses, pay-period/payment/employment types) lives in `src/assets/data/*.json` and is re-exported through [globals.tsx](src/constants/globals.tsx).
